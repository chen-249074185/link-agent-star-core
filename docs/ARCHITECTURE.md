# 架构设计与技术决策（LinkAgent）

> 本文说明系统的整体架构、模块划分与关键技术选型，以及每个选择背后的取舍（"为什么这么选、为什么不选另一种"）。

## 一、项目定位

LinkAgent 是一个**全域自适应多端 AI 智能助手**：Java 单后端，微信 + 小程序 + Web 三端接入，覆盖"对话 / 工具调用 / 工作流编排 / 知识库"完整链路。核心业务场景是**异地求职租房全自动决策工作流**。

## 三、模块划分

| 模块 | 职责 |
|---|---|
| `adapter/` | 通道适配：微信 / Web / 小程序统一成内部 `AgentMessage`，隔离各端 SDK |
| `scene/` | 场景识别（手动指令 > 关键词快筛 > LLM 兜底）与场景策略（每场景的模型/工具/记忆/风格） |
| `llm/` | LLM 客户端统一接口（DeepSeek 实现），含流式与工具调用；多模型路由 |
| `skill/` | 技能契约与实现（天气/通勤/打分/风控…），含 Mock 占位与组合技能 |
| `governance/` | 治理内核：技能执行前的五道安检 + 限流 + 高危确认 |
| `workflow/` | 轻量编排引擎（串行/循环/分支/容错）+ 租房决策工作流 |
| `mcp/` | MCP 双轨：客户端接入 + 房源采集入库；独立 Server：RAG / Crawl / 猎聘 |
| `memory/` | 记忆：瞬时（Redis）+ 短期（MySQL 流水）+ 每日摘要压缩 |
| `user/` | 用户体系：注册登录、JWT、账号合并、人设 |
| `infra/` | 配置、统一响应/异常、traceId、鉴权过滤器 |

## 四、两条运行链路

- **自由问答**：任意原子技能可单独调用。消息 → 场景识别 → LLM 工具循环（模型决定调哪个技能）→ 治理安检 → 执行 → 回填 → 回复。
- **任务工作流**：输入完整租房需求（城市 + 预算 + 通勤上限）→ 判定命中 → 直接跑 `WorkflowEngine` 流水线（**跳过 LLM**，纯确定性编排）：
  片区就业分析 → 房源筛选 → 通勤成本测算 → 风险识别 → 加权打分 → 生成《租房决策报告》。

## 五、技术选型总表

| 层 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | Java 21 + Spring Boot 3 | 生态成熟、类型安全、并发与容器化友好 |
| LLM | DeepSeek（对话 + 工具调用）；DashScope（Embedding / 文生图 / 语音） | 统一 `LlmClient` 接口，可切换 |
| 工具协议 | MCP（本地 Skill + MCP Server 双轨） | 标准化工具接入，进程隔离 |
| 存储 | MySQL + MyBatis（业务）、Redis（治理/记忆）、SQLite + sqlite-vec（向量） | 各取所长，见决策 |
| 鉴权 | JWT（用户轨）+ Admin Token（管理轨） | 无状态、多端通用 |
| 推送 | SSE（打字机流式） | 单向流，简单可靠 |
| 部署 | Docker + docker-compose | 一键起多服务 |
| 文档 | SpringDoc OpenAPI | 接口可视化调试 |

## 六、关键设计决策（为什么这么选 / 为什么不选另一种）

### D1 · 单体应用，而非微服务
- **背景**：单人开发、多端接入、低 QPS。
- **决定**：模块化单体（清晰分包），需要进程隔离的地方用 MCP Server 独立进程。
- **放弃**：Spring Cloud 微服务——拆分成本高、运维重，当前规模收益为负。
- **影响**：部署简单；模块边界靠包结构约束，必要时可再拆。

### D2 · 不用 Kafka / RabbitMQ（消息队列）
- **背景**：交互是**同步请求-响应**（用户发一句话，等一个回复），并发低。
- **决定**：直接同步调用 + Spring 线程池（`CompletableFuture` 异步落库/压缩）。
- **放弃**：Kafka/RabbitMQ——用于**高吞吐、削峰、跨服务解耦**；本项目没有这类需求，引入只会增加一个必须运维的中间件和"消息最终一致性"复杂度。
- **影响**：链路简单、可追踪（traceId 贯穿）；将来若有多消费者/削峰需求再引入。

### D3 · 自研轻量工作流引擎，而非 Camunda / Flowable
- **背景**：业务编排固定（6 道工序），需要串行/分支/循环/容错。
- **决定**：自研 `WorkflowEngine`（节点 + 上下文 + 执行栈），几十行核心逻辑。
- **放弃**：Camunda/Flowable 等 BPMN 引擎——功能远超需求，学习/集成/运维成本高。
- **影响**：代码可控、易测；代价是只覆盖当前需要的编排能力。

### D4 · MCP 双轨（本地 Skill + MCP Server）
- **背景**：既要快速写本地工具，又要接入标准化/可复用的外部能力。
- **决定**：本地 `Skill` 接口 + MCP Server（stdio）两条轨，统一注册进技能清单、统一过治理。
- **放弃**：全部写成本地代码（难复用/难隔离）或全部 MCP 化（简单工具也要起进程，过重）。
- **影响**：兼顾开发效率与扩展性；双轨统一治理，行为一致。

### D5 · MySQL + MyBatis，而非 JPA / Hibernate
- **背景**：SQL 需要精细控制（分区、聚合、显式列）。
- **决定**：MyBatis + Mapper XML，SQL 显式可见。
- **放弃**：JPA/Hibernate——自动生成 SQL 在复杂查询下难优化、黑盒。
- **影响**：SQL 可控、性能可预期；代价是需手写映射。

### D6 · Redis 承担治理与记忆
- **背景**：限流、单日限次、高危确认、跨轮记忆需要**快速过期 + 原子操作**。
- **决定**：Redis（TTL 过期、INCR 原子计数、Set 持久化）。
- **放弃**：纯内存（重启即失）或 MySQL（高频读写不划算）。
- **影响**：治理与记忆具备 TTL 语义与原子性；本地开发用 Memurai/Redis 兜底。

### D7 · SQLite + sqlite-vec 做向量库，而非 pgvector / Milvus / Qdrant / ES
- **背景**：RAG 是 MCP 子进程，单用户、语料小（城市房源资料），要**零运维**。
- **决定**：SQLite 单文件 + `sqlite-vec` 扩展，随 RAG MCP 子进程内嵌。
- **放弃**：pgvector（要额外 PG 服务）、Milvus/Qdrant（独立服务，杀鸡用牛刀）、ES（重、偏全文检索）。
- **影响**：随 jar 自包含、零外部依赖；代价是超大规模/多写并发非其强项——当前场景不需要。

### D8 · LLM 分工：DeepSeek 对话 + DashScope 多模态
- **背景**：需要对话/工具调用，也需要 embedding、文生图、语音。
- **决定**：对话 + 工具调用用 DeepSeek（成本低、Function Calling 稳定）；Embedding/文生图/语音用 DashScope（DeepSeek 不提供）。
- **放弃**：单一厂商——无法同时覆盖对话与多模态；接口层 `LlmClient` 统一，便于切换。
- **影响**：各取所长；代价是维护两个 API Key。

### D9 · 鉴权双轨：JWT（用户）+ Admin Token（管理端）
- **背景**：用户端多端通用；管理端是内部工具、无多用户。
- **决定**：用户端 JWT（`sub=userId` 贯穿对话/知识库/记忆），管理端静态 Token。
- **放弃**：给管理端也做完整账号体系——过度设计。
- **影响**：简单、够用；管理端凭证不落 localStorage。

### D10 · 治理内核"五道安检"
- **背景**：LLM 会调工具，需要防止越权、危险操作、无限循环、滥用。
- **决定**：技能执行前统一过五关——技能存在、场景白名单、高危确认、单轮步数上限、单日限次。
- **放弃**：把风控散落在各技能里——不可控、易漏。
- **影响**：所有工具（含 MCP）统一受控；主工作流还会过滤无关技能。

### D11 · 流式用 SSE，而非 WebSocket
- **背景**：回复是**服务端 → 客户端**的单向流（逐 token 打字机）。
- **决定**：SSE（`text/event-stream`）。
- **放弃**：WebSocket——双向能力用不上，且更重、需额外握手/心跳。
- **影响**：基于 HTTP、实现简单、断线可重连；代价是纯单向（本场景足够）。

### D12 · 部署用 Docker Compose，而非 Kubernetes
- **背景**：单机部署、服务固定（MySQL/Redis/app/liepin-mcp 四服务）。
- **决定**：docker-compose 一键起。
- **放弃**：K8s——单机小规模下，编排/运维收益远小于成本。
- **影响**：一条 `docker compose up -d` 即可；将来上云/多副本再迁移。

### D13 · 技能三层划分（MAIN / SCENE / EXT）
- **背景**：技能越来越多，工作流里不能混入无关工具。
- **决定**：`MAIN`（主线配套）/ `SCENE`（支线）/ `EXT`（通用扩展）；工作流执行时过滤掉全部 EXT。
- **放弃**："平铺"技能清单——工作流容易被无关工具污染。
- **影响**：职责清晰、主线纯净；新增技能只需标注类型。

### D14 · 用 MCP 协议，而非各写一段函数调用
- **背景**：工具要能被 LLM 调用，还要能复用、能进程隔离。
- **决定**：采用 MCP（Model Context Protocol）标准化工具接入，本地 Skill 与 MCP Server 双轨统一注册。
- **放弃**：每个工具写死成一段 JSON Schema 直接塞给 LLM——不可复用、无隔离、越加越乱。
- **影响**：协议统一、能力可独立成进程；代价是多一层握手。

### D15 · 自研 Skill / LlmClient，而非 LangChain4j / Spring AI
- **背景**：需要可控的工具循环、治理钩子、多厂商切换。
- **决定**：自研 `Skill` 契约 + `LlmClient` 统一接口。
- **放弃**：LangChain4j / Spring AI——封装厚、抽象多，治理/流式/多厂商细节不好插，也偏离"理解原理"。
- **影响**：链路透明、易测；代价是自行维护厂商 API 格式翻译。

### D16 · MyBatis（XML 显式 SQL），而非 MyBatis-Plus / JdbcTemplate
- **背景**：查询需显式控制，避开自动生成 SQL 的黑盒。
- **决定**：MyBatis + Mapper XML。
- **放弃**：MyBatis-Plus（便捷 CRUD，但复杂查询仍写 SQL 且多一层）、JdbcTemplate（样板多）。
- **影响**：SQL 可见可控；代价是手写映射。

### D17 · 三级记忆（瞬时 / 短期 / 每日摘要），而非单一记忆
- **背景**：要跨轮连贯、跨天记忆，又不能无限膨胀。
- **决定**：瞬时=Redis(TTL 30min，超轮压缩)；短期=MySQL 流水；每日=定时压缩成摘要（闲聊遗忘）。
- **放弃**：只用 Redis（重启丢、无长期）或只用 MySQL（高频读写、无 TTL）。
- **影响**：连贯/持久/成本兼顾；代价是链路略复杂。

### D18 · traceId 全链路日志（可观测性）
- **背景**：多端多线程，出问题要能把一条消息全链路串起来。
- **决定**：每请求生成 traceId，写 MDC、贯穿日志与响应头，异步线程显式透传。
- **放弃**：靠时间戳/关键字捞日志——并发下对不上。
- **影响**：一条 traceId 还原全链路；代价是异步处要手动传 MDC。

### D19 · 场景策略 YAML 配置化，而非硬编码
- **背景**：不同场景要不同模型/工具/记忆/风格。
- **决定**：`application.yml` 配置每场景策略，启动时校验（场景齐全、工具名在清单内）。
- **放弃**：写死在代码分支——改策略要改代码、易漏。
- **影响**：改策略零代码；代价是多一处配置校验。

### D20 · 流式与工具循环"合流"
- **背景**：既要打字机效果，又要有工具调用。
- **决定**：有工具时走工具循环、最终答案流式输出；无工具时按场景路由到对应模型直接流式。
- **放弃**：二选一——要么没工具，要么没流式。
- **影响**：体验与能力兼得；代价是维护两套路径。

### D21 · Mock / 真实双轨开关（开发期可离线跑）
- **背景**：真实 MCP 未就绪时也要能开发与测试工作流。
- **决定**：`mock-enabled` 开关，true 用 Mock 占位技能，false 走真实 MCP，编排逻辑零改动。
- **放弃**：等依赖齐了再开发——阻塞进度。
- **影响**：可离线开发与回归；代价是维护一套 Mock 数据。

### D22 · 单库单表，而非分库分表 / 读写分离
- **背景**：单用户量级、数据量小。
- **决定**：MySQL 单库，按 userId 逻辑隔离。
- **放弃**：分库分表 / 读写分离——规模不需要，徒增复杂度。
- **影响**：结构简单；将来量大再拆。

### D23 · 多端身份互通（账号合并）
- **背景**：微信 / 邮箱 / 用户名可能是同一个人。
- **决定**：以 userId 为唯一身份；绑定邮箱/微信时做账号合并（保留发起方）。
- **放弃**：各自独立账号——同一人数据割裂。
- **影响**：多处登录共享记忆/知识库；代价是合并逻辑需谨慎。

### D24 · 鉴权用 JWT，而非服务端 Session
- **背景**：多端（微信/小程序/Web）与 SSE 场景。
- **决定**：JWT（`sub=userId`）；SSE 用 query 传 token 兜底。
- **放弃**：Session——跨端/无状态扩展差，SSE 带 Cookie 也别扭。
- **影响**：无状态、多端通用；代价是要处理失效/续期。

### D25 · 前端用原生 HTML + SSE，而非前端框架
- **背景**：页面不复杂（对话/知识库/管理），主打快速交付。
- **决定**：原生 HTML/JS + `EventSource`/fetch，免构建。
- **放弃**：Vue/React——引入构建链，当前页面规模下收益有限。
- **影响**：零构建、静态即部署；代价是复杂交互不如框架。

### D26 · DTO/契约用 record（Java 21）
- **背景**：大量不可变的数据载体。
- **决定**：`record`（SkillContext / SkillMeta / AgentMessage 等）。
- **放弃**：POJO + Lombok——样板多、可变性难控。
- **影响**：简洁、不可变、线程安全；代价是需留意 JSON 序列化注解。

### D27 · 文件解析放服务端（PDFBox / POI），而非外部 CLI
- **背景**：知识库要支持 pdf / docx 上传。
- **决定**：服务端用 PDFBox + POI 纯 Java 解析。
- **放弃**：外部文档识别 CLI 子进程——实测解析 docx 会超时卡死。
- **影响**：稳定、无外部进程；代价是格式覆盖取决于库能力。

### D28 · 房源采集走"文件 + 重建索引"，而非直写向量库
- **背景**：采集数据要可查、可人工校对。
- **决定**：抓取 → 解析 → 写 `rag_data/{城市}.txt` → 重建索引；用户可手改 txt 再重建。
- **放弃**：直接写向量库——不可读、不可人工修正。
- **影响**：数据可读可编辑；代价是多一步重建。

### D29 · MCP 管理类工具不注册给 LLM
- **背景**：管理工具（超管删库等）不能被模型调用。
- **决定**：`rag_admin_*` 前缀工具只给管理接口直连，注册时按前缀跳过，不进 LLM 工具清单。
- **放弃**：全量注册——模型可能越权调用管理接口。
- **影响**：权限边界清晰；代价是需按前缀约定过滤。

## 七、如何新增一个技能（简）

1. 实现 `Skill` 接口（`meta()` 自报家门 + `execute()` 干活），放 `skill/impl/`。
2. 加 `@Component`（自动进技能清单）；Mock 占位技能额外加条件注解。
3. 启动日志确认技能清单出现新技能，按需标注 `SkillType`。

> 更细的使用说明见 `docs/FRAMEWORK.md`，接口契约见 `docs/API.md`。
